# How I used AI on this task

AI was used as a force multiplier: it wrote most of the code quickly; the value I added was
the specification, the review, and the verification.

## What was AI-assisted

Most of the code was generated by an AI coding agent (Claude) working from the task PDF,
with the architecture and security requirements set up-front and every change verified by
running lint, typecheck, tests and a live deployment.

| Area | AI share | Notes |
|---|---|---|
| Monorepo scaffolding, tsconfig/eslint/jest/vite config | High | Pure boilerplate — the fastest win. |
| DTOs, `class-validator` rules, Zod schemas | High | Password rules live in one module on the API and are mirrored by the web app. |
| Auth service (sign-up/sign-in/refresh/sign-out) | High, constraint-driven | Generated against an explicit security spec (below), then reviewed line by line. |
| Tests (unit, e2e, component) | High | Test *targets* were chosen deliberately: reuse detection, generic errors, no hash leakage, whitespace edge cases. |
| UI components & visual design | High | Art direction given up-front (warm paper + ink + lime accent, product mock in the brand panel, accessible forms). |
| README, this file | Medium | Edited for accuracy. |

## Prompts / approaches that worked well

- **Constraint-first prompts.** Specifying the security model ("tokens in httpOnly SameSite=Strict cookies, same-origin deployment; refresh tokens opaque, hashed at rest, rotated on every use, reuse revokes the family; argon2id with OWASP params; generic sign-in errors with a dummy-hash verify") produced far better code than "add JWT auth".
- **Asking for failure modes before code.** "How does this refresh flow break with two tabs?" surfaced the concurrent-refresh race → a 10 s grace window server-side and a single-flight refresh client-side.
- **Turning the PDF's requirement list into tests first**, then asking for edge cases: whitespace-only names, whitespace counted as a "special character", >128-char passwords, unknown body properties.
- **Feeding back raw tool output** (tsc/eslint/test failures, deploy logs) instead of paraphrasing.

## What had to be corrected or decided differently

1. **Exception filter** — the first version had a convoluted branch that could mislabel string-bodied `HttpException`s; rewritten to a simple, explicit mapping. Unknown errors are logged with a stack and returned as a generic 500.
2. **Error alert re-mounting** — a draft keyed the sign-in alert on `Date.now()` to replay its shake animation, which re-mounted it on *every keystroke*. Replaced with an attempt counter.
3. **Lost redirect after sign-in** — the "redirect if already authenticated" guard fired before the page's own `navigate(from)`, so users always landed on `/app`. The guard now honours `location.state.from`.
4. **Sign-in validation** — the strength rules are deliberately *not* re-applied on sign-in (that leaks the policy and would lock users out if it tightens).
5. **tsconfig** — generated config used `baseUrl`, which the installed TypeScript rejects; removed.
6. **Dependency versions** — the newest majors (Nest 12, TS 7, Vite 8) had just shipped; pinned to proven versions (Nest 11, Mongoose 8, TS 5.9, Vite 7) rather than ship an assessment on fresh majors.
7. **Accepted trade-off** — sign-up returns 409 for an existing email (clear UX) at the cost of email enumeration, mitigated by a 10 req/min limit on credential endpoints.

## Verification

- `npm run lint && npm run typecheck && npm test` — green locally (API 24 tests, web 11 tests).
- API e2e suite runs against a real MongoDB service container in GitHub Actions.
- Deployed to Railway and exercised against the live URL: sign-up, duplicate email, wrong password, protected endpoint, refresh, sign-out.
